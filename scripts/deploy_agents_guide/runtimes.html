Same code, other targets

agents-cli adds the other targets to an existing project. The repo's alt/cloud-run branch is this lab's agent after:

agents-cli scaffold enhance . --deployment-target cloud_run
agents-cli deploy                 # runs gcloud run deploy with the generated settings

For GKE, --deployment-target gke adds Kubernetes manifests and Terraform for a cluster, and agents-cli deploy builds the image, applies Terraform and runs kubectl apply. Keep sessions and memory in Agent Platform so pods stay stateless, and use Workload Identity for the pods.

The MCP servers in this lab already run on Cloud Run: tools that other teams own usually belong there, next to the agent runtime rather than inside it.

Departments as separate agents (A2A)

The lab deploys one app with four agents. When departments own their agents, deploy each as its own Agent Runtime and let the front door find them. The repo's alt/multi-agent-a2a branch is a tested proof of concept (see docs/A2A.md there):

  • Discovery. Every Agent Runtime deployment registers itself in Agent Registry. The concierge lists the registry at startup, fetches each agent's A2A card and adds it as a RemoteA2aAgent; no URL is configured anywhere.
  • Identity. The concierge calls with its own Agent Identity and passes the employee in A2A request metadata; the department agent acts for that employee, and its MCP server logs the right person.
  • Observability. Each agent gets its own traces, which also removes the managed Online Monitor's multi-agent skip.
  • Not there yet. Agent Gateway passes and logs the calls, but classifies them as the Google APIs endpoint, so a policy rule per agent doesn't apply yet. A turn costs a second hop: 7–12 s warm, about 50 s when both agents are cold.
