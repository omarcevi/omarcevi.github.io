Deploying Your Agents on Google Cloud

In about 40 minutes you take a multi-agent HR and IT assistant from a repo to production shape: Agent Runtime with its own Agent Identity, Memory Bank, Agent Gateway in front of every tool call, a trace for every turn, and evals that gate deploys.

What you build

Workplace Assistant is one front door for HR and IT at Kuzey Labs, a fictional company. All employees, salaries, tickets and handbook pages are made up.

  • concierge routes, handles small talk, and refuses anything outside HR and IT.
  • hr_policy_agent answers from the handbook (in-process BM25 over six markdown files) and looks up published salary bands.
  • leave_agent reads balances and books leave in the HRIS (an MCP server), and can add leave to the employee's own Google Calendar.
  • it_desk_agent opens and tracks tickets in the ticketing MCP server.
  • A third MCP server, compensation, holds individual salaries. The agent's code can reach it. In step 4 a policy stops it.

Before you start

  • A Google Cloud project with billing enabled, where you are Owner (the lab grants IAM roles and binds an access policy). A fresh project is easiest.
  • A browser. Everything runs in Cloud Shell, which already has gcloud, uv, git and Python.
  • agents-cli 1.11 or later: uv tool install --force "google-agents-cli>=1.11" (step 1 does this; Cloud Shell's preinstalled agents-cli is older).
  • Region europe-west1. Every product in the lab is available there; the model runs on the global endpoint (step 2 explains why).
  • Cost: about USD 0.30–1 per participant, mostly Gemini tokens. Run the teardown at the end.
PREVIEW FEATURESSemantic governance policies and Agent Identity on Cloud Run are Preview. The lab's main path uses only generally available features. Steps 4 and 6 each have a fallback script in case a feature is not available in your project.

The six steps

Each step has the same shape: how it works (one diagram), commands to paste, the output you should see, a check (./scripts/check.sh N), if this fails, and a box on taking this to a customer.

  • STEP 1 · 5 MINSet upAPIs, three MCP servers on Cloud Run, Agent Registry, and the gateway building in the background.
  • STEP 2 · 8 MINDeployagents-cli deploy to Agent Runtime with Agent Identity; chat with it.
  • STEP 3 · 6 MINRememberTell it your team once; see Memory Bank recall it in a new session.
  • STEP 4 · 8 MINSecureBind Agent Gateway; watch a salary lookup get denied by policy while HRIS keeps working.
  • STEP 5 · 5 MINObserveOne leave request as a trace; the dashboard with blocked calls.
  • STEP 6 · 7 MINEvaluateEval gate, Online Monitor, and a production failure turned into a test.

How the lab works

Checkpoint branches. step-0-start … step-6-evaluate hold the repo as it should look after each step. If you join late or your copy breaks, check out the branch for the step you finished and continue; ./scripts/check.sh with no argument checks that step.

git fetch origin
git checkout step-3-remember   # state after step 3
./scripts/check.sh             # checks step 3

Your cloud resources are what count. The branches only change files in the repo. If an earlier step never ran in your project, run its commands first; every script is safe to run again.

Two terminal tabs help. Deploys take a few minutes; start one in tab 2 and keep reading in tab 1.
