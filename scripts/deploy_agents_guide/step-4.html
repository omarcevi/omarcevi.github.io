How it works

Two kinds of authority. When the agent calls the HRIS it acts as itself: it gets an ID token for its own Agent Identity, and Cloud Run checks roles/run.invoker (for external APIs the same idea is 2-legged OAuth, client credentials). When it adds leave to your calendar it acts for you: that needs your consent once (3-legged OAuth). Agent Identity Auth Manager runs the consent flow, keeps the tokens in a Google-managed vault, and hands ADK your token when the tool runs.

Agent Gateway checks every outbound call, in order:

  1. Agent Registry resolves the destination. Unregistered destinations are refused unless a policy names them.
  2. IAM access policy. IAP evaluates the policy for the agent's identity: who may reach which MCP server, endpoint, or even which tool, with conditions on tool names or annotations such as read_only_hint. Deny rules win over allow rules.
  3. Content checks (optional): a semantic governance policy (Preview) judges each tool call the model proposes against a plain-language rule such as “never retrieve an individual's compensation”, and Model Armor screens MCP tool calls for prompt injection and sensitive data.

Default deny. Once bound, the gateway refuses everything not allowed, including the agent's own calls to Gemini, Sessions, Memory Bank and telemetry. That's why setup.sh registered a google-apis endpoint and the policy allows it.

Egress and ingress. This lab uses an egress gateway (Agent-to-Anywhere): it governs what the agent calls. An ingress gateway (Client-to-Agent) sits in front of the agent instead and screens query/streamQuery traffic with Model Armor or a semantic policy; it must be in the agent's project and region. An agent can be bound to both.

Who owns the policy. The security or platform team writes the access policy; the agent team registers its tools and asks for access. The policy file in this repo is short on purpose:

Run

Make sure the gateway finished building in the background (step 1):

tail -1 .setup-gateway.log      # should say GATEWAY READY

Apply the access policy, then bind the agent to the gateway (a redeploy, about 4 minutes):

./scripts/secure.sh
agents-cli deploy --project $PROJECT_ID --update-only --agent-identity --no-confirm-project \
  --agent-gateway-egress=projects/$PROJECT_ID/locations/europe-west1/agentGateways/workplace-gw \
  --update-env-vars GOOGLE_API_ENABLE_RUNTIME_BOUND_TOKEN=false

The gateway inspects TLS, so the agent's certificate-bound tokens can't pass through it unchanged; GOOGLE_API_ENABLE_RUNTIME_BOUND_TOKEN=false switches the agent to unbound tokens for Google APIs, as the gateway documentation requires.

Ask the same salary question as in step 2, and check that HRIS still works:

agents-cli run --url "$AGENT_URL" --mode adk "What is the salary band for an L5 in Istanbul?"
agents-cli run --url "$AGENT_URL" --mode adk "How many leave days do I have?"

See the denial in the logs, from the agent's side and from the gateway's side:

gcloud logging read 'labels."event.name"="workplace.tool_blocked"' --freshness=15m --limit=3 \
  --format='value(timestamp,jsonPayload.tool,jsonPayload.reason)'
gcloud logging read 'resource.type="networkservices.googleapis.com/Gateway" AND jsonPayload.authzPolicyInfo.result="DENIED"' \
  --freshness=15m --limit=3 --format='value(timestamp,httpRequest.requestUrl,jsonPayload.mcpInfo.method)'

No Agent Gateway in your project? Use the fallback

If .setup-gateway.log says GATEWAY FAILED, or the gateway is not available in your project, block the compensation server with plain Cloud Run IAM instead. The agent's code still calls it; IAM refuses it. The script prints how this differs from the gateway.

./scripts/fallback_step4.sh
agents-cli run --url "$AGENT_URL" --mode adk "What is the salary band for an L5 in Istanbul?"
./scripts/check.sh 4             # the log reason is permission_denied instead

Removing an IAM grant takes one to three minutes to apply. If the salary band still comes back, wait a minute and ask again.

Optional: the employee's own Calendar (3-legged OAuth)

An instructor demo, since it needs an OAuth client and a consent screen. Outline:

  1. Create an OAuth client (type Web application) in APIs & Services → Credentials, and enable the Google Calendar API.
  2. Create the Auth Manager provider: 
    gcloud agent-identity auth-providers create calendar-3lo --location=europe-west1 \
  --three-legged-oauth-client-id=CLIENT_ID --three-legged-oauth-client-secret=CLIENT_SECRET \
  --three-legged-oauth-authorization-url=https://accounts.google.com/o/oauth2/v2/auth \
  --three-legged-oauth-token-url=https://oauth2.googleapis.com/token
  3. Add the provider's redirect URL (…/authProviders/calendar-3lo/oauthcallback on agentidentitycredentials.googleapis.com) to the OAuth client.
  4. Let the agent use it: gcloud agent-identity auth-providers add-iam-policy-binding calendar-3lo --location=europe-west1 --role=roles/agentidentity.user --member="$AGENT_PRINCIPAL"
  5. Set CALENDAR_AUTH_PROVIDER=projects/$PROJECT_ID/locations/europe-west1/authProviders/calendar-3lo in .env and redeploy. leave_agent now has create_calendar_event; the first call asks the employee for consent through a client that handles ADK's adk_request_credential event, then Auth Manager keeps the token.
If this fails
Every question fails right after binding (Reasoning Engine Execution failed)
The access policy hasn't applied yet: policy changes take one to three minutes to reach the gateway. Wait and ask again. Gateway logs show DENIED for …aiplatform.mtls.googleapis.com until then.
Google API calls return 401 through the gateway
The agent is still using certificate-bound tokens. Redeploy with --update-env-vars GOOGLE_API_ENABLE_RUNTIME_BOUND_TOKEN=false.
Everything is DENIED, minutes after the policy
The policy binding must target the project number (secure.sh does this), while the names inside conditions use the project ID, as gcloud agent-registry … list prints them. Gateway logs show numbers, which is misleading.
498 errors
A Google API hostname the agent uses is not registered. Find it in the gateway log (jsonPayload.enforcedGatewaySecurityPolicy.hostname), add it to infra/gateway/platform-endpoints.txt, run ./scripts/setup.sh --only registry.
The salary band still works
The agent isn't bound yet (the deploy is still running), or you're on the fallback and IAM hasn't applied (one minute).
Undo the block
./scripts/fallback_step4.sh --undo for the fallback; for the gateway, remove the deny rule and run ./scripts/secure.sh again.
Taking this to a customer
  • Ownership. Security owns the access policies (organization or folder level for guardrails, project level for each agent). Agent teams register tools and request access. Start in DRY_RUN enforcement and read the logs before you enforce.
  • Ask the security team: Is there a central governance project for the gateway and registry? Is iam.managed.disableAccessPolicyBindings enforced? Which external SaaS endpoints may agents reach? Who reviews tool annotations such as readOnlyHint?
  • End-user identity. In this lab the agent tells the MCP servers who the employee is (X-User-Email), and they trust the agent. In production, pass the employee's own token (3-legged OAuth through Auth Manager) or a signed assertion, and have the server verify it.
  • Trade-off to discuss: behind the gateway the agent uses unbound tokens for Google APIs. The gateway compensates (every call is authorized and logged), but say it out loud.
  • Cost: the gateway and IAP add per-call processing; semantic governance and Model Armor add model calls per tool call. Check the Agent Platform pricing page for the current rates.
