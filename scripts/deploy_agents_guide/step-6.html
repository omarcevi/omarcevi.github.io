Step 6 · Evaluate

7 min

Gate changes on an eval set, score live traffic with an Online Monitor, and turn a production conversation into a new test case.

checkpoint branch step-6-evaluate

How it works

The eval set lives in evals/cases.yaml: twenty prompts with what should happen. agents-cli eval run runs the agent on each one (locally, against fresh copies of the MCP servers) and grades the traces:

  • Right tool, right arguments (tool_trajectory): did it call submit_leave_request with next Friday's date, open a P1 ticket for a stolen laptop, and never call forbidden tools?
  • Routed to the right specialist (routed_to_expected_agent).
  • Refuses salary questions (no_compensation_leak): no individual salary figure in any answer, and a referral to the People Partner when asked.
  • Grounded in the handbook (grounding_v1): an LLM judge from the Gen AI evaluation service checks every sentence of policy answers against the handbook.

The first three are small Python functions that run locally; grounding calls the evaluation service. agents-cli exits 0 whatever the scores, so evals/gate.py compares them with evals/thresholds.yaml and fails the build: that is what makes it a gate.

Online Monitors score live traces. Every ten minutes the monitor samples recent traces of the agent and runs judge metrics (final response quality, tool use quality, hallucination, safety). It reads prompts and answers from the telemetry events that step 1 turned on.

Run

Offline evals (about two minutes):

./scripts/eval.sh

Online Monitor. Create it with the script, which also lets the Vertex AI service agent read traces:

./scripts/monitor.sh

Or in the console: Agent Platform → Optimize → Evaluation → Online monitors → New monitor. Select agent workplace-assistant, name it workplace-quality, region europe-west1, unit Traces, All traces → Continue. Keep the four default metrics → Continue. Sampling percentage 100, max samples per evaluation job 20 → Set up. Then grant the service agent access, or the monitor shows Failed:

gcloud projects add-iam-policy-binding $PROJECT_ID --condition=None \
  --member=serviceAccount:service-$PROJECT_NUMBER@gcp-sa-aiplatform.iam.gserviceaccount.com \
  --role=roles/observability.viewAccessor

Close the loop. Pick a production conversation, ideally one where the answer was wrong, and add it to the eval set. If you don't have one, try this, which should not book anything (29 October is Republic Day for the Istanbul office):

uv run python scripts/ask.py "Book 29 October off for me."      # note the session id
uv run python scripts/session_to_eval_case.py SESSION_ID --id my_regression
# edit the TODO lines of the new case at the end of the behaviour list in evals/cases.yaml:
#   expected_agent: leave_agent     forbidden_tools: [submit_leave_request]
uv run python evals/build_datasets.py && ./scripts/eval.sh behaviour

Eval gate (handbook): PASSED ==> Creating online monitor workplace-quality (sampling 100%, max 20 traces per run) ✔ requested: projects/…/operations/…

About ten minutes later the scores show under Deployments → workplace-assistant → Dashboard → Evaluation, and per trace on the Traces tab.

Check

./scripts/check.sh 6
✔ eval behaviour passes the thresholds ✔ eval handbook passes the thresholds ✔ online monitor: workplace-quality ==> Step 6 checks passed.

Fallback

If Online Monitors are not available to you, or the evaluation service is down, run the local part of the eval and look at monitor results recorded during a rehearsal:

./scripts/fallback_step6.sh
If this fails
only 4 of 5 cases ran
A model call timed out during generation and agents-cli dropped that case. Run ./scripts/eval.sh again.
A metric below its threshold
The gate lists the failing cases with the judge's explanation. Open artifacts/eval/SUITE/results_*.html for the full traces.
The monitor shows Failed
Usually the service agent permission above. Delete the monitor and create it again after granting.
No monitor scores
The first run is up to ten minutes after creation and only scores traces that exist by then. Ask the agent a few questions.
The API returns INVALID_ARGUMENT creating a monitor
The request must not set semconvVersion; monitor.sh sends the same body as the console.
Taking this to a customer
  • Who writes the cases. Domain owners (HR, IT) write the expected behaviour; engineers make it executable. Every incident becomes a case before the fix ships.
  • Thresholds are a business decision. Agree per metric what blocks a release: a leaked salary is a hard 1.0; tone can be 0.8. Run the gate in CI before every deploy.
  • Monitors read real prompts. Treat them like any system that processes employee data: sampling rate, retention of scores and rationales, and who can see the Evaluation tab.
  • Cost: judge metrics are billed as model tokens. A monitor at 100% sampling of busy traffic adds up; use a lower percentage and a max samples per run.
