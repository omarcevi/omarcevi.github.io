Step 1 · Set up

5 min

In this step, you put the repo in Cloud Shell, enable the APIs, and deploy the three MCP servers that the agent calls.

checkpoint branch step-1-setup

How it works

Each tool server is a service with an owner. The HRIS, ticketing and compensation systems are separate MCP servers on Cloud Run (FastMCP, streamable HTTP). One image serves all three servers. An environment variable selects the server. Each service accepts only callers with roles/run.invoker. No service has a public URL.

Read-only tools have a label. Each tool has MCP annotations, for example readOnlyHint. Agent Registry keeps them with the tool list. Gateway policies can use them.

Agent Gateway starts now, because it takes time. The creation of Agent Gateway and its IAP authorizer takes about six minutes. setup.sh starts this work in the background. You use Agent Gateway in step 4.

Run

Open in Cloud Shell →

The button copies the repo into Cloud Shell. It also opens a tutorial panel that shows the commands for each step, each with a copy button. Keep this guide open for the explanations.

In the Open in Cloud Shell dialog, select Trust repo. Then click Confirm. If you do not select Trust repo, Cloud Shell runs in ephemeral mode and deletes your files when the session ends. Google's documentation also says that these sessions do not get your credentials.

When Cloud Shell asks to use your credentials, click Authorize. Click the button only one time, because each click makes another copy of the repo. You can also open Cloud Shell and clone the repo yourself. Then run these commands:

# skip the clone if you used the Open in Cloud Shell button
git clone https://github.com/omarcevi/cloud-agents-workshop.git
cd cloud-agents-workshop

gcloud config set project YOUR_PROJECT_ID
uv tool install --force "google-agents-cli>=1.11"
export PATH="$HOME/.local/bin:$PATH"   # Cloud Shell has an older agents-cli in /usr/local/bin
./scripts/check.sh 0                 # tools, login, billing
./scripts/setup.sh                   # APIs, MCP servers, registry (about 2 min); the gateway keeps building in the background

Expected result

==> Project your-project (123456789012), region europe-west1 ==> Enabling APIs (takes a minute the first time) ✔ APIs enabled ==> MCP server image mcp-servers:a440ce4b9b7f ✔ built with Cloud Build ==> Deploying 3 MCP servers to Cloud Run (IAM-only, scale to zero) ✔ hris-mcp ✔ ticketing-mcp ✔ compensation-mcp ==> Registering MCP servers and Google APIs in Agent Registry ... ==> Agent Gateway workplace-gw (background, about 6 minutes) ✔ started; follow it with: tail -f .setup-gateway.log ==> Setup finished in 111s. Next: ./scripts/check.sh 1

Check

./scripts/check.sh 1
✔ hris-mcp ready, 403 without a token (IAM-only) ✔ ticketing-mcp ready, 403 without a token (IAM-only) ✔ compensation-mcp ready, 403 without a token (IAM-only) ==> Step 1 checks passed.

The 403 response without a token is correct. No service on Cloud Run is open to the internet.

If this fails
agents-cli: command not found, or check.sh 0 reports an agents-cli older than 1.11
Cloud Shell has an older agents-cli in /usr/local/bin. Cloud Shell uses it until ~/.local/bin is first on your PATH. Run the two install lines above again in this terminal. In a new Cloud Shell tab, also run the export line.
Billing ✘ in check.sh 0
In the console, link a billing account to the project. If you do not have a billing account, work with the person next to you.
Cloud Build fails with a permission error
In a new project, Google needs about one minute to give roles to the build service account. Wait one minute. Then run ./scripts/setup.sh again. The script does not create a resource again if it exists. If your organization does not allow default grants, give roles/cloudbuild.builds.builder to the Compute Engine default service account.
FAILED_PRECONDITION or SERVICE_DISABLED immediately after you enable the APIs
Google needs some time to apply a new API to all its systems. Run ./scripts/setup.sh again.
.setup-gateway.log ends with GATEWAY FAILED
Read the error above that line. Possibly, Agent Gateway is not available to your project yet. You can still do steps 2, 3, 5 and 6. In step 4, use ./scripts/fallback_step4.sh.
Take this to a customer
  • Talk to the platform team first. Ask which region you must use (data residency), which project contains the agents, and which organization policies apply. Two organization policies can stop this lab. iam.allowedPolicyMemberDomains can refuse principal:// members. iam.managed.disableAccessPolicyBindings stops the access policy of the gateway, and it is on by default in new organizations.
  • Tools have owners. The HRIS team owns the HRIS MCP server, its IAM and its tool annotations. Agree who registers servers in Agent Registry and who can grant run.invoker.
  • Cost: Cloud Run with min instances 0 costs nothing when it gets no requests. One image build costs a few cents of Cloud Build time.
